# S2.5 — Strategy Version Stamping & the CI Gate

**Session:** S2.5. Phase 2, closing item. Done when: counters segment per
version, and CI fails on an unapproved V1 logic diff.

---

## 1. What `strategy_version` is

`app/versioning/strategy_version.py::compute_strategy_version()` returns a
12-hex-char fingerprint of exactly two things:

1. **The raw bytes of 5 files**: `momentum_strategy.py`, `entry_engine.py`,
   `risk_manager.py`, `exit_engine.py`, `entry_gate.py`. The first four are
   I1's own literal list of "V1 decision logic." `entry_gate.py` is added
   because it is the shared price-geometry invariant and gate every entry
   decision passes through (ARCHITECTURE.md §2, §6) — a change there is
   exactly as decision-relevant as a change to the other four.
2. **One config value living outside those files**: `app.main`'s
   `SCANNER_ENTRY_GATE_CONFIG` (min_rr, min_setup_percent, min_option_quality,
   max_spread_pct). Every other decision threshold found during this session's
   audit — `RR_MIN_THRESHOLD`, the regime ATR multiplier table, the
   `EMA_PULLBACK` stop floor, `entry_gate.py`'s own `EntryGateConfig`
   defaults — is a hardcoded literal already inside one of the 5 files, so
   hashing the file bytes already captures it. Duplicating those values here
   would be redundant, not safer.

**This list defines the scope of "V1 decision logic" for versioning
purposes.** If I1's own definition is ever amended, update
`V1_DECISION_LOGIC_FILES`, not the other way around.

### What is deliberately excluded

- Telegram gating thresholds (`TELEGRAM_MIN_RR` etc.) — Telegram is a
  transport, not a decision engine (architectural invariant 3); they gate an
  alert, not a trade.
- Position sizing / affordability config (`OPTION_STOP_LOSS_PCT`,
  `ACCOUNT_SIZE`, …) — these affect *what gets recommended and how big*, not
  *whether a setup is a valid entry*. A future session may decide sizing
  belongs in scope; that is a deliberate extension, not an oversight here.
- Anything env-driven inside the 5 files — audited during this session and
  found not to exist (only `entry_gate.py::env_int` is env-driven, and it is
  an unused-internally helper exported for other modules).

### Caching

Cached per-process (`compute_strategy_version(use_cache=True)`, the default).
Files don't change while a process runs — config already requires a restart
for changes to take effect (CLAUDE.md conventions) — so re-hashing 5 files and
importing `app.main` on every trade, alert, and evidence row would be pure
waste. `strategy_version_manifest()` always recomputes, for audit/debugging
and for the CI gate.

## 2. Where it is stamped

**Frozen at open, like risk geometry — never recomputed at close.** A trade's
`strategy_version` must reflect the code that decided *it*, not whatever is
running when it happens to close.

| Site | What |
|---|---|
| `paper_trade_manager.py::open_paper_trade` | Stamped onto the trade dict at creation |
| `paper_trade_manager.py::_append_paper_trade_event` | New `strategy_version` column in `paper_trade_events.csv` |
| `trades/exit_snapshot.py::create_exit_snapshot` | New field, carried into `trade_exit_snapshots.csv` |
| `analytics/trend_capture.py::build_trend_capture_row` | New `Strategy Version` column in `trend_capture_analysis.csv` |
| `alerts/telegram_alerts.py` (`maybe_send_paper_entry_alert`, `maybe_send_trade_exit_alert`) | Added to `dispatch_metadata`, visible in `telegram_dispatch_audit.jsonl` |

### Not stamped in this session — a real gap, not an oversight

`candidate_snapshot`, `decision_waterfall`, and `rule_evaluation` are
DB-backed tables with discrete typed columns (verified: not JSONB), so adding
`strategy_version` to them requires a schema migration. **No migration was
written or applied.** Per CLAUDE.md convention, migrations are manual and
deliberate (`DATABASE_DIRECT_URL`, never from the scanner) — applying one
against the live Neon database is not something this session does
unilaterally. If DB-backed evidence needs version segmentation later, that is
a new migration (`01N_strategy_version_columns.sql`), applied by the operator,
not retrofitted here.

### The CSV header-compatibility hazard, extracted

Both `trend_capture_analysis.csv` and `paper_trade_events.csv` had the same
"a new column silently misaligns an already-open day file" hazard that S1.4
found and fixed for `trade_exit_snapshots.csv`. Rather than re-solve it a
third time, the fix was promoted to `app/utils/csv_append.py::append_row`, and
all three writers now share it. Three independent copies of the same
correctness-critical logic is worse than one shared, tested one.

## 3. Backfill rule

`app/versioning/strategy_version.py::UNVERSIONED = "v0-unversioned"` —
EXECUTION_PLAN.md's own instruction: *"existing trades pre-date versioning.
Stamp them `v0-unversioned` and exclude them from any promotion decision
rather than guessing."*

Applied at every evidence boundary that reads a trade that might predate this
session: `create_exit_snapshot`, `build_trend_capture_row`,
`_append_paper_trade_event`, `_alert_strategy_version`. Never a bare `None` —
`None` would silently pass through pandas groupbys and comparisons in ways a
named sentinel does not.

## 4. Segmenting the evidence counters

`app/ui/cache/validation_state_builder.py::_strategy_confidence` — the
Strategy Confidence formula (METRICS.md §5) — now groups by `Strategy
Version` before computing `evidence_days`/`completed_trades`, and reports
`rule_change_allowed` **only for the currently-running version's slice**.
`by_version` in the returned payload carries every version's counts, for
visibility.

**This is a real, observable behavior change**, confirmed by updating
`tests/test_validation_state_builder.py`: fixtures that previously
contributed to confidence with no version stamp at all now count as
`v0-unversioned` and are correctly excluded from the current version's
`rule_change_allowed`. This is the intended effect, not a regression — the
whole point of segmentation is that evidence collected under different
decision logic must not inflate confidence in the logic running today.

**Consequence worth stating plainly: this resets accumulated evidence to
zero the moment this session's changes are treated as a new version.**
`SCANNER_ENTRY_GATE_CONFIG`, `entry_gate.py`, and the other 4 files were not
touched this session (verified: the seeded baseline hash matches what's on
disk), so there is no reset *yet* — but the next time any of those 5 files
changes, whatever evidence has accumulated starts over. That is the intended
mechanism, and it is also the reason `by_version` is reported rather than
discarded: a version change should be visible, not silent.

**Not segmented in this session**: `evaluate_promotion`'s feature-promotion
gate (`promotion_rules.py`) and the V1.0 Evidence Freeze threshold
(METRICS.md §5, "100-200 completed trades," still human policy, not code —
unchanged by this session). Only the Strategy Confidence counters were in
scope here; the other two gates were not asked for and are a reasonable next
extension, not done by implication.

## 5. The CI gate

**Before this session: no CI existed at all** (confirmed —
`docs/OPERATIONS.md` §11 already flagged this). `.github/workflows/ci.yml` is
new, with two jobs:

1. **`test`** — runs the full pytest suite. Enforces I5 (test count only
   rises) as a build failure, not a convention.
2. **`strategy-version-gate`** — runs
   `tools/check_strategy_version_approved.py`, which computes the current
   `strategy_version` and fails the build if it is not present in
   `app/versioning/approved_strategy_versions.json`.

This directly converts I1 from documentation discipline into a build
failure: **a diff that changes V1 decision logic changes the hash, and an
unreviewed hash fails CI.** The only way past it is adding the new hash to the
approval file in the same PR — an explicit, reviewable, diffable act. The
gate makes no judgment about whether a V1 change is a *good* idea; that
judgment is the reviewer's, exercised by choosing whether to add the
approval entry.

**A real finding while building this**: the test suite does not even
*collect* without a real-looking `POLYGON_API_KEY` — `technical_indicators.py`
constructs a `polygon.RESTClient` at import time, which raises if the var is
unset. Verified: a placeholder value (`ci-placeholder-not-a-real-key`, never
used for a real request during the suite) is sufficient — all 367 tests pass
with no `.env` file present at all, given just that one variable. The CI
workflow sets it explicitly; this is not a secret and is safe to commit in
plain text.

**Seeded baseline**: `app/versioning/approved_strategy_versions.json`
contains one entry, `30566aefd474`, verified to match
`compute_strategy_version()` for the code as committed at the start of this
session. `tests/test_strategy_version_gate.py` asserts the real checked-in
file currently approves the real current version — if that test ever fails,
either the baseline is stale or a V1 file changed without going through the
gate.

## 6. What this does not do

- Does not touch V1 decision logic itself (I1 fully intact — this session's
  diff is entirely in `app/versioning/`, `app/utils/csv_append.py`, stamping
  call sites, evidence-counter segmentation, and CI infrastructure).
- Does not migrate any DB table (§2).
- Does not segment the V1.0 Evidence Freeze or feature-promotion gates (§4).
- Does not retroactively version historical evidence — pre-existing CSV rows
  and DB rows have no stamp and are read as `v0-unversioned` wherever a
  reader checks for one; nothing rewrites them.
